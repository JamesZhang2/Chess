# Problem Log

This file is used to track the many problems that I encountered during this project, and my solutions (or *Proposed solution*s) to these problems.

- Problem: `perft` tests run extremely slowly.
  - Skip checking move legality for moves generated by `getLegalMoves`.
  - When checking whether our king is in check, we iterate through the opponent pieces one by one and return early if one of them attacks the king, rather than getting the set of all squares attacked by the opponent and checking whether our king is in one of them.
  - In `updateWinner`, set `hasLegalMoves` to true and exit early if one of the pieces have legal moves, rather than computing the set of all legal moves.
  - Use `char[][]` instead of `Piece[][]` in `MailboxBoard`. Represent an empty square as `(char) 0` rather than `null`.
  - Use bulk counting in `perft`: Previously, we increment the counter if we reach depth 0. Now, we skip going to depth 0 and add the size of the set of all legal moves to the counter at depth 1.
  - Implement `BitmapBoard`: represent each piece type as a long, where a1 corresponds to the least significant bit of the long. Setting a bit to 1 represents that that piece type appears at that location. Then we can use bitwise operations in the methods to speed them up.
- Problem: `MailboxBoard` and `BitmapBoard` has a lot in common, and we don't want to duplicate the code.
  - Extract common code to an abstract `Board` class.
- Problem: We don't want to duplicate the test cases for `MailboxBoard` and `BitmapBoard`.
  - Create an abstract test class `BoardTest` with abstract `createBoard` methods. Call `createBoard` in the tests to get a board. The tests `MailboxBoardTest` and `BitmapBoardTest` can then extend `BoardTest` by supplying their different ways of creating a board.
- Problem: Getting the least significant nonzero bit in a bitmap is an important operation, and scanning from the right to the left is slow.
  - Use De Bruijn Multiplication. This works as follows: A 64-bit De Bruijn sequence has different values in its most significant 6 bits with different left shifts (0 to 63). So, we can isolate the LS1B, multiply it by the De Bruijn sequence (equivalent to left shifting), then read from a lookup table to see how much it has been left shifted. See [this link](https://www.chessprogramming.org/BitScan) for details.
- Problem: Dynamically computing attacks in a bitmap board based on how pieces move is slow.
  - Use lookup tables for pawn, king, and knight attacks based on their locations on the board.
  - (*Proposed solution*) Use lookup tables for bishop, rook, and queen attacks as well. Use a bitmask to filter out the irrelevant pieces and only retain the pieces that are potentially blocking the bishop, rook, or queen. Then use a map whose keys are the bitmaps of the filtered pieces and whose values are the attack bitmaps. (We can also use maps for different directions and then take the bitwise OR to further save memory.)
- Problem: Duplication in `move` logic for Mailbox and Bitmap boards.
  - Refactor `move` and extract the common parts into the `Board` abstract class. First check whether move is legal, then make the move using `setPiece` and `removePiece` (abstract methods to be overridden by `MailboxBoard` and `BitmapBoard`). Take care of special cases like castling, en passant, and promotion.
- Problem: Maven runs the same tests twice.
  - Previously we had both `run: mvn -B package --file backend/pom.xml` and `run: mvn -B test --file backend/pom.xml`. We can delete the second one since the first one (building with Maven) already runs the tests.
- Problem: Ad-hoc parsing of moves (given by `HumanCLIPlayer`) is prone to error.
  - Use regex instead of ad-hoc parsing. Use capture groups to single out each part of the Standard Algebraic Notation (SAN), like capture, promotion, castling, checks, and checkmates. Test extensively.
- Problem: No single source of truth if both players are allowed to modify board state.
  - Create a GameController that contains both players and the board. The board stored in the GameController is the single source of truth. Players can tell the controller what move they want to make based on a clone of the board passed to the player. They can't modify the original board directly, and the GameController is in charge of actually making the move on the board.
- Problem: The `Move` class doesn't support non-move actions like resigning, offering draw, and accepting draw.
  - Use an `Action` class that includes different types of actions.
- Problem: It's difficult for the human CLI player to tell what square it is.
  - Add an option to print the board with coordinates on the side.
- Problem: Minimax player still tries to recursively evaluate when the game has ended, resulting in incorrect values since there are no legal moves.
  - Check whether the game has ended with `board.getWinner()`, and return the evaluator's value if the game has ended.
- Problem: After searching several levels of the game tree, the `posFreq` map used to detect threefold repetition gets extremely large, and the search becomes very slow.
  - Previously, `updateWinner` searches through the entire `posFreq` table to check if any value is 3 or more. Now, we added a parameter `incremental` that allows it to only check the last position.
  - Previously, `undoLastMove` only decrements the frequency count of a position, keeping entries whose frequencies have gone down to 0; now, it removes the element from posFreq if the frequency goes down to 0.
- Problem: We get a `NullPointerException` for `bestMove` in `MinimaxAIPlayer` in certain situations.
  - This is due to our initialization of `bestMove` to `null` and `bestEval` to negative or positive infinity (depending on whether we're maximizing), and only updating it when we find a move that beats `bestEval` (strictly greater or less than it). Since we encoded the eval of white winning as positive infinity and the eval of black winning as negative infinity, if we can't escape checkmate, we won't be able to find a move that beats `bestEval`. We can fix this by returning the resign action if `bestMove` is null after our search, since we can't escape checkmate.
- Problem: When we use Axios in the React frontend and Spring Boot in the Java backend, it doesn't work:  The backend is able to receive the requests, but the frontend cannot receive the responses. The console shows an error message like `Access to XMLHttpRequest at 'http://localhost:8080/' from origin 'http://localhost:5173' has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present on the requested resource.`
  - This is because modern browsers disabled Cross Origin Resource Sharing (CORS), which means sharing resources from one domain to a different domain. CORS can lead to security problems, so they are often disabled. To deal with this, we add the annotation `@CrossOrigin(origins = "http://localhost:5173/")` to the top of the REST controller class `AppController` (or set `origins = "*"` to allow all origins, but this should only be in development).

  - Need to `export` the functions that we want the other files to use.
- Problem: The frontend receives a FEN from the backend to update the board state, which side to move, move count, etc, while the frontend sends a Move object to the backend to tell it what the next move will be. We need to maintain some states in the frontend like where the pieces are so that we can render them.
  - Use `useState` in React to maintain states. This is needed because we want React to rerender the board when the states change. For example, `const [pieces, setPieces] = useState(startPos);`. Note that we should use `const` instead of `let` because we're not changing `pieces` directly, but rather updating its value through `setPieces`.
- Problem: We only want to call `initGame` once at the beginning of the game, but if we put the axios call directly in the `Game()` constructor body, it will be called repeatedly when React rerenders.
  - Use `useEffect` with an empty dependency array. This will ensure that it's run only once. Note that `useEffect` takes in a lambda and a dependency array, so we need to wrap the axios call with a lambda. According to the `useEffect` documentation, the code in `useEffect` will run every time React rerenders where any value in the dependency array has changed. If we pass in an empty dependency array, the effect will only run after the initial render. In contrast, if we omit this argument, the effect will run after every render.
- Problem: We want to implement a two-click move where we select an initial square and a destination square. Storing the squares in a regular variable doesn't work.
  - Use `useState` to store the initial square (and also the destination square if it's a promotion). This will allow React to keep the value across renders. In contrast, regular variables get reset with every render.
- Problem: If we put `handleSquareClick` outside of the `Game` function, we will have to pass in the states like the initial square we clicked, leading to clumsy code.
  - In React-style functional programming, it is a good idea to nest functions like `handleSquareClick` inside of the `Game` function so that the states can be accessed. This is different from Object-Oriented programming, where classes have private variables and methods in that class can access those variables.
- Problem: In Spring Boot, using a raw `Map` as the parameter for `@RequestBody` does not allow type checking.

This is better than using a raw `Map` since we get type safety and we can use validation annotations (like `@NotNull`). Similarly, for the response that we want to send to the frontend, we can create a custom class (or record) and send it to the frontend after wrapping it in a `ResponseEntity`.

- Problem: Currently, a challenge has three possible states: pending, resolved, and canceled. We want to only poll pending challenges. - Problem: When waiting for opponent in `waitForOpponent`, we can move our opponent's pieces if we make a legal move.
  - When handling square clicks, check both the color of the piece and the side of the player to make sure that a player can only move their own pieces.
- Problem: We want to use different piece square tables for the opening/middle game vs. the endgame. For example, in the opening/middle game, we want the king to be tucked safely in the corners, but in the endgame, we want the king to be centralized. However, we need a way to tell if the current game is in the opening/middle game or the endgame phase.
  - Use a material-weighted phase system, where each piece (excluding pawns and kings) contribute some weight to the phase. We then take a convex combination of the opening/middle game piece square table and the endgame piece square table.
- Problem: The current minimax algorithm has trouble finding the fastest mate because white delivering mate is scored at +Infinity regardless of the number of moves, and similarly -Infinity for black delivering mate. The algorithm therefore faces several equally good options and has to choose one randomly. Eventually it will stumble into a mate, but this may take a lot of moves.
  - Use a large score like 100000 to represent the eval of white delivering mate (and the negative of that for black delivering mate), and then subtract the number of moves to mate for white. That is, white to mate in 1 is scored as 99999, white to mate in 2 is scored as 99998, etc.
- Problem: Searching through the whole tree in minimax takes a long time.
  - Use [alpha-beta pruning](https://en.wikipedia.org/wiki/Alpha%E2%80%93beta_pruning) to prune branches that our opponent will never allow since they already have better options (from a previously searched move).
- Problem: The bot makes unfavorable trades in complicated capture chains, or would sometimes hang pieces out of nowhere.
  - We need to implement [quiescence search](https://www.chessprogramming.org/Quiescence_Search): Even if the depth reaches 0, we should keep searching, but only for captures. Only evaluate "quiet" positions where there are no more captures available. This is needed to avoid the horizon effect, where the bot stops searching right after they captured a piece thinking that they won material, but the next move which the bot didn't see is their opponent taking a piece, leading to a net loss of material for the bot.
  - I added a parameter for the max depth of quiescence search so that we can adjust it to make time-accuracy tradeoffs.
- Problem: During quiescence search, getting all the legal moves and filtering out the ones that aren't captures takes a long time.
  - Modify `getLegalMoves` to take a parameter `capturesOnly`. If `capturesOnly` is true, we'll only try pseudo-legal moves that are captures.
- Problem: We want to know if our alpha-beta search algorithm is working correctly.
  - Write test cases to compare the evaluations of minimax with and without tuning. The evaluation should be the same.
- Problem: We want the top level of minimax to return both the best eval and the best move, but the recursive calls of minimax to only return the best eval.
  - Write a different method at the top level that also keeps track of the best move in addition to the best eval.
- Problem: If we want to take "mobility" into account in evaluation, we can't just switch the side-to-move to the other side since it might lead to illegal positions where a side is in check but it's not their turn to move. Also, getting the set (or count) of all legal moves is a costly operation, almost equivalent to doing one more level of search. In addition, if mobility is related to the number of legal moves, this would encourage the AI to give checks since checks limit the number of legal moves for the other side. However, giving checks is not always the best idea especially if they can be easily blocked.
  - (*Proposed solution*) Only count pseudo-legal moves (ignoring checks).
- Problem: Using FENs as keys in [transposition tables](https://www.chessprogramming.org/Transposition_Table) (dynamic programming memo tables so that we don't have to do the same computation over and over again) is slow, since computing the FEN string from a position takes a lot of time. In fact, through testing, it's slower than not using transposition tables at all for the depths that I'm currently considering.
  - Use [Zobrist hashes](https://www.chessprogramming.org/Zobrist_Hashing) as keys.
  - Only update Zobrist hashes incrementally in `move()`, rather than recomputing them from scratch after every move.
  - Store the states of previous positions (`char[][] pieces` for Mailbox boards, `long[] bitmaps` for Bitmap boards, as well as states like castling, en passant, etc.) in history, rather than storing the FEN string in history and parsing them every time we `undoLastMove()`.
  - Also store the Zobrist hashes of previous positions in history so that we don't have to recompute them when we `undoLastMove()`.
  - Use FENs only for communicating with frontend, not for saving the board state or for keys in a transposition table in the backend.
  - Also use Zobrist hashes as keys for `posFreq` in checking threefold repetition. This has a chance of causing false positives due to hash collisions but it's very unlikely (expected number of entries to cause a hash collision can be computed with the birthday paradox).
    - Note that when undoing the last move, we should decrement the frequency in `posFreq` (and remove the entry when the frequency reaches 0) for the position **before** we restore the Zobrist hash rather than after.
- Problem: Currently we return the eval if `eval >= beta` or `eval <= alpha`. However, the top level method will then face some seemingly equally good options, but one of them is `alpha` while the other is `<= alpha` (which can potentially be much worse than `alpha`).
  - This might be easily fixable if the top level method only updates its best move if the eval is strictly greater (for maximizer) than the current best eval, but there might still be problems with floating point errors.
  - Instead, we set a small constant `EPSILON` so that we only prune the branch if `eval < alpha - EPSILON` rather than just `eval <= alpha` (and similarly for `beta`).
- Problem: We don't know if an entry in the transposition table is of a lower depth, making the value inaccurate.
  - Also store the depth in the entry and only use the entry if the current search depth is less than or equal to the depth of the entry.
- Problem: If we return early from alpha-beta pruning, the returned `eval` is not the exact `eval` but only a lower or upper bound, so putting it in the transposition table may be misleading.
  - Distinguish the different kinds of entries with a `Type` enum (`EXACT`, `LOWER_BOUND`, or `UPPER_BOUND`). We can use `EXACT` values in all situations, but we can only use `LOWER_BOUND` values for beta cutoffs and `UPPER_BOUND` values for alpha cutoffs.
- "Problem": If we don't enable alpha-beta pruning, using or not using transposition tables give the same eval. However, if we do enable alpha-beta pruning, they sometimes give different results.
  - This does not necessarily mean that there's a bug in the program, since if we enable alpha-beta pruning, it might be expected that a different value will be returned with vs. without using transposition tables. This is because the lower bounds and upper bounds that we got from a previous evaluation may be different from the ones that we get from this evaluation (since the depths may be different, or we could be exploring the game tree in a different order).
- Problem: A lot of code duplication exists between regular search and quiescence search.
  - Refactor the code to merge the two methods into one, with a `capturesOnly` parameter. Use different transposition tables for regular vs. quiescence search. If `capturesOnly`, we initialize `maxEval` to the stand-pat value (static evaluation) instead of initializing it to -Infinity; also, only consider captures in `getLegalMoves`.
- Problem: Using a `Map<Long, TpnTableEntry>` as the transposition table leads to an out-of-memory error at depth 4 (and depth 10 quiescence search).
  - Change the transposition table to be a fixed-size array (say with 1 million entries). Store the Zobrist hash in the entries so that we can compare them, since the bucket number is now the Zobrish hash mod the array size, rather than just the Zobrist hash. Use the fixed-size array as a cache and evict entries according to some policy (e.g. keep the entry with larger depth) in case of a conflict.
